# Benchmarks

Every number here comes from a result file in `benchmarks/results/`, produced by
`scripts/measure_latency.py` (the table is generated by `--summarize`). Phase 7 adds load
tests at 1 / 10 / 25 / 50 streams to this page.

## Phase 4: end-to-end latency at 10 concurrent streams

**Target (spec):** p95 < 50 ms from the moment a window's last sample arrives at ingest to
the moment its prediction is published, at 10 concurrent streams.

**Result: met in all 6 runs.** p95 was 32.8 to 37.9 ms with one worker and 21.6 to 45.8 ms
with three. No window was lost in any run (1,160 windows each).

### Setup

- 10 sessions in parallel, one per held-out subject (fold-0 test subjects of the served
  model, none used in training), streamed at **real-time speed** for 60 s each by the
  replayer: packets of 16 samples (100 ms) at 160 Hz, 64 channels.
- Window jobs: 2 s window + 0.5 s pad, every 0.5 s per session, so 20 jobs/s in total.
- Served model `eegnet-motor-1.0.1`, one ONNX Runtime thread per worker.
- Everything runs in Docker Desktop on a Windows 11 laptop (Docker VM: 8 CPUs, 8 GB).
  All timestamps come from containers on the same VM clock.
- Each configuration was run 3 times. One run is not enough here: identical runs differ
  by nearly 4x at p99 (28 vs. 108 ms with three workers, see below).

```powershell
docker compose up -d --wait
python scripts/measure_latency.py --sessions 10 --workers 1 --seconds 60
python scripts/measure_latency.py --sessions 10 --workers 3 --seconds 60
python scripts/measure_latency.py --summarize
```

Stages (each prediction carries them, so they always add up):
**total = ingest** (window complete → job produced) **+ queue** (job produced → read by a
worker: ingest's write buffer, `XADD`, waiting in the stream) **+ worker** (read →
published: preprocessing the whole batch, one ONNX call, encoding). Ingest is under 1 ms at
p99 in every run, so it is left out of the table.

Live balanced accuracy over the 623 windows with a single known label was 48.2% in every
run (predictions are deterministic). It is a small sample of 10 people: the
cross-subject estimate of 45.7% in [`MODEL_RESULTS.md`](MODEL_RESULTS.md) is the reliable number.

### Analysis

1. **Queueing dominates, not compute.** With one worker, the median window spends 7.9 to 11
   ms in the queue and 5 to 7 ms in the worker; inference itself is 1.9 to 2.4 ms per batch
   (median).
   All 10 sessions started together, so their windows complete within the same few
   milliseconds every 0.5 s: a burst of 10 jobs. The worker takes what is there (mean
   batch about 4), and the rest of the burst waits for that batch. This is the worst case
   for a burst: real headsets would not be phase-aligned.
2. **Batching never waits, and it pays off under bursts.** A read takes whatever jobs are
   available and returns at once; there is no "wait until 32 jobs or 5 ms" timer. Batches
   form only when jobs are already waiting, which is exactly when a batch is cheaper than
   one ONNX call per window. Batch size is recorded on every prediction.
3. **Three workers halve the median but not the tail.** p50 drops from 14 to 19 ms to
   about 9 ms, because a burst is split three ways. p95 and p99 do not improve reliably:
   the slowest windows come in **time clusters** where all 10 sessions are slow together
   and *every* stage slows down at once (preprocessing that normally takes 1 ms took 17 ms).
   That is CPU being taken away from the containers (Docker Desktop VM / Windows host), not
   the pipeline; more workers compete for the same CPUs during such a stall. Measuring on
   Linux without the Docker Desktop VM would separate the two.
4. **Warm-up matters for a freshly started worker.** Before the model was warmed up at
   start, a new worker's first seconds had inference calls of 17 to 101 ms (normally ~2
   ms), which dominated the max latency of a scale-out run (144 ms). Workers now run the
   model on dummy batches of every size before joining the consumer group (0.65 s).

## Fault tolerance (tests, not benchmarks)

- **Worker killed mid-stream** (`test_killing_a_worker_mid_stream_loses_no_windows`):
  two worker processes, one hard-killed (`TerminateProcess` / `SIGKILL`) while it held
  unacknowledged jobs. Every window ingest produced got a prediction; the dead worker's
  jobs were reclaimed by the survivor after 1 s of idleness.
- **Overload past the stream cap** (`test_overload_trimming_is_counted_as_lost`): three
  sessions at 40x real time into one deliberately slow worker with `ns:windows` capped at
  ~20 jobs. Most jobs are trimmed before any worker reads them. Every trimmed job is
  counted as lost, and the stream accounting balances exactly:
  `entries-added = acked + lost_trimmed_undelivered + lost_trimmed_pending + dead_lettered + pending + lag`.
